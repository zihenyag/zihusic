# macOS AirPlay implementation notes

Investigated on macOS 15.6.1, 2026-10-23–24.

## Apple documentation

- [Supporting AirPlay in your app](https://developer.apple.com/documentation/avfoundation/supporting-airplay-in-your-app): the `AVAudioSession.longFormAudio` setup is explicitly for iOS, tvOS, and watchOS. Native macOS has no equivalent public audio-session configuration.
- [Tune up your AirPlay audio experience, WWDC23](https://developer.apple.com/videos/play/wwdc2023/10238/): AirPlay Audio supports synchronized receivers and enhanced buffering; AVPlayer/AVQueuePlayer or sample-buffer renderers provide playback, but the session does not expose Music's native macOS group manager.
- [AVRoutePickerView](https://developer.apple.com/documentation/avkit/avroutepickerview): public system device selection. The macOS SDK marks `prioritizesVideoDevices` unavailable on macOS.
- [Use AirPlay to stream audio](https://support.apple.com/en-us/105068): Music can select several speakers; Mac Control Center can select only one.
- [AVPlayer.setRate(_:time:atHostTime:)](https://developer.apple.com/documentation/avfoundation/avplayer/setrate(_:time:athosttime:)): synchronized starts require `automaticallyWaitsToMinimizeStalling = false`. Violating this raises an Objective-C exception, which was observed in the previous local companion implementation.
- [AVPlayer.preroll(atRate:completionHandler:)](https://developer.apple.com/documentation/avfoundation/avplayer/preroll(atrate:completionhandler:)): preloads the playback pipeline before starting.
- [AVPlayerItem.timebase](https://developer.apple.com/documentation/avfoundation/avplayeritem/timebase) and [CMSyncConvertTime](https://developer.apple.com/documentation/coremedia/cmsyncconverttime(_:from:to:)): relate media presentation time to the host clock. The companion converts between device timelines instead of assuming that two sampled `currentTime` values share a clock.
- [AVPlayer.sourceClock](https://developer.apple.com/documentation/avfoundation/avplayer/sourceclock): replacing the appropriate audio device clock can cause drift. This app leaves device clocks under AVFoundation's control.

## Comparison with the installed Apple Music application

Read-only inspection of the installed Music binary found `ComputerSpeakerGroup`, `RemoteSpeakerGroupAudioDevice`, `SpeakerGroupManager`, `iTunesAudioContext`, `associatedAudioDeviceID`, and `AVCFPlayerSetAudioDeviceUID` references. These establish that Music contains its own group/device routing machinery. They do not reveal its complete synchronization algorithm.

Music is signed with Apple's internal `com.apple.avfoundation.allow-system-wide-context`, `com.apple.avfoundation.allows-access-to-device-list`, and `com.apple.avfoundation.allows-set-output-device` entitlements. This third-party app does not request or impersonate those entitlements. Public SDK support alone does not establish Music feature parity.

Apple's [WebKit AVFoundation SPI](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/PAL/pal/spi/cocoa/AVFoundationSPI.h) and [audio target picker](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/graphics/avfoundation/objc/AVRoutePickerViewTargetPicker.mm) declare/use the guarded audio-context interfaces used by this adapter. SPI in Apple's source is not a public SDK guarantee.

## Current behavior (2026-10-24)

- The main button always presents the compact app panel, with no + button. Checkboxes represent playback preference, independent of route membership. Stopping uses native mute when supported, otherwise native receiver volume 0; the preferred level is retained and restored on resume. A stopped receiver stays joined and receives the common timeline. Sliders remain present/usable while stopped, and every speaker may be stopped.
- Native discovery stays active outside the panel and automatically adds/rejoins exposed or already-known native handles. On this macOS host it still exposes no unselected receivers: AVOutputDeviceDiscoverySession (features 1/5/65535), MediaRemote discovery, local and XPC FigRouteDiscoverer wrappers, and FigEndpointManager returned empty lists. Bonjour sees the receiver but provides no usable native routing handle. A minimal descriptor using the receiver's real RouteUID failed to add it (destination-change status 3). The precise filtering mechanism is unverified; Music has internal device-list entitlements absent from this app. `NativeAirPlayEnrollment` now automates the native picker instead: it requests normal macOS Accessibility consent, opens only this app's AirPlay popover, checks each enabled unchecked remote row once, and closes the popover. It never traverses other apps or global windows. Without consent, no selection is automated. This is an Accessibility-based workaround, not successful enumeration through private routing APIs.
- With remote outputs selected, `GroupedAudioOutput` uses one `AVAssetReader`, shared AAC packets and one `AVSampleBufferRenderSynchronizer`, with the AirPlay renderer added first. It calls `setRate(_:time:)` without a future host deadline so the receiver's confirmed start anchor governs the common timeline. This replaces the failed companion AVPlayer/drift-correction implementation.
- Audio buffers, flushes, playback commands and timers run on a dedicated serial audio queue. Discovery/route IPC and receiver-level writes use separate serial queues; a blocked route request cannot hold mute/volume behind it. Identical pending level writes are coalesced without indefinitely postponing a mute when route notifications repeat. The main actor receives snapshots and never waits for these operations.
- `AirPlayAudioAsset` uses Apple's native M4A export to prepare a temporary AAC transport copy. Original files remain intact; standalone local playback still uses the original. Copies are reused by source path/size/modification identity and pruned to a small recent cache (normally 12 files / 256 MiB, preserving the newest two).
- Both renderers receive packets from a single reader. Fan-out retains at most 16 unread buffers while either renderer is negotiating. Pauses retain queued audio; seeks flush both renderers and rebuild the reader with the requested time range. Generations reject stale preparation, progress and seek callbacks.
- Local selection/volume controls the local renderer; each receiver's supported volume uses the native output device. Local calibration shifts only the local packet timestamps, from -3000 to +3000 ms in 5 ms steps. This is manual adjustment, not microphone-measured calibration or an individual offset for every remote receiver.
- Playback checkboxes update immediately without connection spinners. Progress indicators represent actual automatic connection only. Playback/volume preferences are saved by receiver ID, mute read-back cannot overwrite preferred volume, and old in-flight snapshots cannot undo later control writes. Re-synchronization flushes/re-anchors the shared timeline without removing receivers.

- A release startup sample also found the main thread blocked opening a lyric sidecar during window restoration. Lyric loading now runs off the main actor in a track-keyed cancellable view task; late results from an old track are ignored. This does not alter lyric typography/layout.

- New launch behavior always enables this Mac and disables receiver playback while retaining saved levels. The shared remote renderer is also muted while no receiver is enabled, preventing enrollment from briefly sounding remotely before receiver-level writes arrive.
- Bonjour `_raop._tcp` additions request another enrollment pass, covering a MacBook that appears after startup. UI enrollment is deferred while the app is inactive, and permission state is checked periodically; the AirPlay button also checks pending work. The system picker may briefly appear during an automatic pass. Manual “AirPlay 全同步” lives in the Playback menu.
- Development builds are ad-hoc signed. Rebuilding changes the code requirement: TCC may show an old toggle as on while rejecting the new binary. In that case refresh only the zihusic entry through System Settings with normal administrator authentication; do not edit TCC databases or reset unrelated apps.

## Validation boundary

On the tested macOS 15.6.1 Mac mini → MacBook Air pair, the user confirmed a short AAC beat was basically aligned after removing the fixed host deadline, then confirmed a 60-second song prototype playing *That Girl* was basically synchronized. After integration and release packaging, the user also confirmed both Macs played *That Girl* basically in sync in the main app.

Twenty-nine local regression tests cover native AAC preparation/cache invalidation, shared-packet pause/seek/resume/end handling, silent-receiver enablement without resetting the timeline, stale-task cancellation, route races, playback/mute/volume preferences, automatic add-only reconciliation using injected native-handle stubs, lyric cache/source refresh, viewport cancellation/positioning and exclusion zones. The control tests do not connect actual speakers. These are software checks, not an acoustic measurement. In the newly packaged main app, native UI inspection confirmed stopping MacBook leaves its route connected, changes native volume from about 0.377 to 0, retains the displayed preferred volume, and restores native volume to about 0.377 on resume. During actual song playback the user confirmed: “能停止并恢复，Mac mini 不受影响”. This validates independent stop/resume on the tested pair; it is not a new acoustic synchronization measurement. Main-app seek, independent volume changes and track changes still need broader hardware coverage; multiple remote receivers remain unverified, and iPad is outside current scope. The guarded private routing adapter is still experimental, and no claim of Apple Music feature parity is made.

After refreshing the stale ad-hoc Accessibility entry for the current release binary, the native-picker automation enrolled MacBook without manual receiver selection and closed the system picker. The compact panel showed this Mac enabled and MacBook disabled, retaining both volume sliders. Relaunching the same authorized build again showed both devices with only local playback enabled. For the app-first/receiver-later case, the user put MacBook to sleep and woke it, then confirmed: “自动出现，默认不出声”. This validates enrollment/default playback on this pair, not an acoustic delay measurement. Native UI checks also confirmed the custom menu hierarchy, working light appearance and sidebar visibility changes.

See [the investigation history](AIRPLAY_RESEARCH.md) for failed approaches and official references.

The 2026-10-24 lyric timing investigation also reproduced a track-change clock leak: the synchronizer updates its timebase asynchronously, allowing the previous time to be published with the new generation. An anchor guard rejects that snapshot; the new regression captured `[2.5, 0, 0, 0]` before the fix and passes afterward. Lyric highlighting now uses the progress UI snapshot without a fixed lead, and old viewport motion is canceled on track changes. The user subsequently accepted the installed build after the clock and menu fixes. This is user acceptance of that build, not a measured acoustic timing result.
